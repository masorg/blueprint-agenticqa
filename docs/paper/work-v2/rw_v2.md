## 2. Related Work

**Review load and LLM reviewers.** Agent-written pull requests are numerous [20, 21] and make review a growing bottleneck [5, 22]. Zhong et al. [1] study over a million reviewed pull requests and find that agents speed up decisions without improving review quality. SEVRA-BENCH [2] shows that review agents can be manipulated by pull-request text, and Kumar et al. [6] warn that artificial benchmarks flatter models. Two studies of human reviewers [3, 4] show that people alone are not a safe backstop. GATE treats the pull-request text as something an attacker may write.

**Regression test selection.** Choosing the tests that a change can affect is a long-studied problem. Safe techniques select every test whose behaviour can change [23]. Ekstazi tracks dynamic file dependencies [24], and Legunsen et al. compare static techniques [25]. Industrial systems trade safety for cost with models trained on history. Predictive Test Selection at Facebook halves the testing infrastructure cost and still reports more than 99.9% of faulty changes [26], and Google describes continuous testing at scale [27]. For Python, NameRTS builds a graph of code names and selects all affected tests for 99.6% of commits while skipping 69.9% of test files on average [28]. pytest-testmon records dependencies at run time, and Section 5.1 compares it with GATE on the same mutants [29]. In the agent era, TDAD gives a test-impact map to the coding agent and lowers regressions from 6.08% to 1.82% on SWE-bench Verified with small open models [30], and CASPER groups the tests of an LLM system into slices and ranks the slices by their chance of regressing after a prompt or model change [31]. GATE's selector belongs to the family of static, safe selection with name-level analysis. It claims no better algorithm.

**Testing LLM and agent systems.** Two recent papers propose test pyramids for these systems. Badagi et al. [7] propose a five-layer pyramid defined by the scope of what is tested, from infrastructure to business outcome, require every prompt to be re-tested after a model change, and gate deployment with thresholds on scores from LLM judges. It is a strategy with illustrative examples and no measurement. Kohl et al. [8] apply the unit, integration, and acceptance pyramid to LLM-based agents, make tests deterministic with scripted model replies and recorded traces, report two detailed case studies, and state that a large-scale study is needed. Both gate a pipeline automatically. Neither selects tests for a change or asks a person to approve one. GATE defines its layers by *the kind of failure they find*, includes a property-based layer, and measures the design.

**Test generation and quality.** Many papers study how to make agents write tests [13 to 17]. This is a different problem, since GATE uses the tests that a project already has. Generated tests often run but are shallow or flaky [9, 10], and mixing property-based with example-based tests finds more bugs [11, 12], which is one reason for several layers. Work on judging agent trajectories [18, 19] relates to the trajectory layer.

**Where the parts come from.** GATE combines existing ideas. Table 1 states, for each part, what exists, what GATE changes, and what is new.

**Table 1.** Where each part of GATE comes from.

| Part | Existing basis | Change | New |
|---|---|---|---|
| Test pyramid | Pyramids built on the scope of what is tested [7, 8]; property-based tests find extra bugs [11, 12] | Layers are defined by the kind of failure. A property layer and two agentic layers are added | Nothing in the idea; the design is measured |
| Selection | Safe, static and dynamic test selection [23, 24, 25, 28] | File-level and name-level analysis of Python imports; any doubt selects all tests | A change that no test reaches is not approved (the uncovered rule); models may add tests and never remove one |
| Plan | Models used to route and classify; keyword rules | Router and classifier only advise. Each has a rule fallback, and the classifier is checked against file-name cues | The plan acts only on the selected tests |
| Execute | Virtual environments and containers | One environment per dependency set; an isolation level set by policy | Nothing in the idea |
| Verdict rule | A CI check that fails when any test fails; pass thresholds on judge scores [7] | The verdict is computed over the selected tests and the uncovered part of the change | Two propositions with short proofs, and attacks that try to break them |
| Status and escalation | Required status checks and reviews; LLM reviewers that can be talked into approving [2] | A comment resolves a flagged change only after the commenter's repository permission is checked | Neither a comment nor the pull-request text can grant approval |

**How GATE differs.** The works above supply parts of GATE, and none supplies the whole. Test-selection techniques [23 to 31] contain no model, return an empty set when nothing is affected, and leave the merge decision to a CI check that is green when nothing ran. The LLM-based works use a model to inform an agent [30] or to rank tests [31], not to extend a safe core. The pyramid papers [7, 8] provide layers, not selection or approval. LLM reviewers [1, 2] let a model decide. GATE contributes the composition and its tested safety. A deterministic core fixes the tests that must run. Models may add tests and cannot remove any (Proposition 1). A change that no test reaches goes to a person, where a plain CI check would turn green. A fixed rule turns the outcomes into a verdict that is published as a status and resolved by a person with repository permission. The evaluation measures the selection against the full suite on mutants of real projects and on real agent-written pull requests (Section 5).
