## 4. Evaluation Design

We ask five questions.

- **RQ1, safety.** Does GATE miss a failure that a full test run shows?
- **RQ2, cost.** How many tests and how much time does GATE save, and how often does it send a change to a person?
- **RQ3, models.** Can a router, a classifier, a test advisor, or the text of a pull request weaken the verdict, and what do models add over rules?
- **RQ4, alternatives.** How does GATE compare with a widely used selection tool on the same changes?
- **RQ5, layers.** What does the test pyramid add?

The reference throughout is a full test run, which is what a plain CI check does. A *regression* is a test that passes at the merge base and fails with the change. GATE *misses* a regression if it neither selects the failing test nor sends the change to a person. We report misses with the upper end of a 95% Wilson interval, which stays above zero when no miss is observed.

**Data.**

- *Mutants of real projects.* Open-source Python libraries with pytest suites at pinned commits: attrs, boltons, click, idna, itsdangerous, jinja, markupsafe, more-itertools, pluggy, sqlparse, and toolz. A mutant changes one source file in one of seven ways: flip a comparison, swap `+` and `-`, swap `and` and `or`, drop a `not`, replace a `raise` with `pass`, negate an `if` condition, or shift a numeric constant. We drew at most 30 per project, round-robin over source files with a fixed seed, and dropped mutants that break test collection. The full suite either fails on a mutant or does not; mutants on which it does not, including equivalent ones, are survivors and cannot be missed. The selector was developed on these projects.
- *Held-out projects.* We named 22 further projects in three batches and pinned each to its last non-merge commit before 2026-09-30 before running any of them. None was used to develop the selector before its first run; the first run exposed a bug in the static core (in validators, batch 2), and after each fix all held-out projects were rerun. Batch 3 was named after the first fix. The coverage-based core was developed later and was itself fixed after misses on held-out mutants (Table V), so no batch is untouched for it. Only {{selHoldRan}} of the {{selHoldAttempted}} could be set up (the others lacked build metadata or test plugins); with the {{selMutProjectsRan}} development projects they make the {{shProjects}} projects of the evaluation.
- *Real defects.* SWE-bench Verified [32] pairs real GitHub issues in {{selSweRepos}} projects with the fixing patch and the tests that fail before the fix. We drew at most 20 instances per project with a fixed seed ({{selSweAttempted}} in all, because several projects have fewer), and excluded instances whose exposing tests could not be matched to discovered test functions by name. Each instance becomes a change that introduces the defect (the tree before the fix with the test patch, and the reverse of the fix as the diff), and GATE has to select an exposing test or send the change to a person. This is a static check: no tests run, a defect counts as caught if an exposing test is selected, and exposing tests exist by construction.
- *Real pull-request traffic (shadow replay).* For each of the {{shProjects}} projects we fixed the 25 most recent pull requests and, as a second batch, the 25 before them, before running any. In a throwaway container we ran the full suite at the merge base (the state a CI check compares against) and at the head, and computed GATE's selection and verdict from the diff, posting nothing. A test is *introduced* if it fails at the head and passes at the merge base, confirmed by two reruns at the head and one at the base. The coverage-based core ran with a fresh recording at every merge base and, on the {{stRan}} pull requests of batch 1 that ran, with one stored recording per project, made at the merge base of its oldest sampled pull request, as a deployment would use it.
- *Platform.* The experiments ran in throwaway Docker containers (non-root, no capabilities, read-only file system, limits on CPU, memory, and processes) on one workstation. The selector and the verdict use no model, so every safety experiment runs without a model provider, which suits organisations that cannot send code to one; only the model studies of RQ3 called model APIs, through OpenAI-compatible clients that an organisation can point at models it hosts itself.
- *Agent-written pull requests.* The files changed by {{selAidevN}} AIDev pull requests in Python repositories [20], and a static selection study of {{selFieldAttempted}} of them drawn with a fixed seed.
- *Demo services.* Two services we wrote with tests for every layer, an inventory API ({{invTests}} tests) and a tool-calling support assistant ({{supTests}} tests), with {{mutValid}} mutants and one planted bug per layer.
- *Attacks.* Hostile routers (all 32 ways of switching the five layers) and classifiers (six behaviours, such as omitting or inventing tests) ran in the real pipeline on the demo services ({{advRouterCases}} and {{advClassifierCases}} cases) and on real projects; hostile test advisors (eight behaviours) on mutants of four projects; and seven kinds of misleading pull-request text on four models, with ordinary text from {{noiseDescriptions}} real AIDev descriptions as a control.
- *Routing.* {{routCommits}} public commits of {{routRepos}} projects, to compare models with a dependency check at recognising agentic projects.

***Cores and comparison.*** We report GATE's static core at file and name level and its coverage-based core, which uses one recorded run of the unmodified project; pytest-testmon [29] ran on the same mutants after its own recorded run, with its default settings and the C tracer of coverage. Because a refinement of the selector changes only which tests are selected, we judge selectors against the failures that the full run showed; the first version also ran its selected tests, and the two agreed. Times are estimated from per-test durations and exclude environment set-up and recording. Shares of tests run are averaged over changes; tests saved are pooled, so large suites weigh more. For $k = 0$ misses in $n$ cases the Wilson bound is about $3.8/n$.

**Models.** gpt-4o (2024-08-06), gpt-4o-mini (2024-07-18), mistral-large-latest, and mistral-small-latest, at temperature 0, with the model name that the API returned recorded in every report. The models matter only for RQ3; newer models could change the grouping and the reports, not the safety results.

**Reproducibility.** Every report records the code version, whether the working tree had uncommitted changes, and a fingerprint of its inputs. Samples were fixed by seeds or pre-registered lists before any run, and every attempt is reported, including those that could not run. A run with a failed model call is marked invalid and is not reported. All numbers in the text are generated from the reports.
