## 2. Related Work

**Review load and LLM reviewers.** Agent-written pull requests are numerous [20, 21] and make review a growing bottleneck [5, 22]. Over a million reviewed pull requests show that agents speed up decisions without improving review quality [1]; review agents can be manipulated by pull-request text [2], artificial benchmarks flatter them [6], and human reviewers alone are not a safe backstop [3, 4]. GATE treats pull-request text as attacker-written.

**Regression test selection.** Choosing the tests that a change can affect is a long-studied problem. Safe techniques select every test whose behaviour can change [23]. Ekstazi tracks dynamic file dependencies [24], and Legunsen et al. compare static techniques [25]. Industrial systems trade safety for cost with models trained on history [26, 27]. For Python, NameRTS builds a graph of code names and selects all affected tests for 99.6% of commits while skipping 69.9% of test files on average [28]. pytest-testmon records per-test dependencies with coverage and reruns the tests whose code changed [29]; Section 5.1 compares it with GATE on the same mutants. For agents, TDAD gives the coding agent a test-impact map [30], and CASPER ranks slices of an LLM system's tests by their chance of regressing [31]. GATE's static core belongs to the family of safe static selection with name-level analysis, and its coverage-based core to dynamic selection. It claims no better selection algorithm.

**Selection and coverage in CI practice.** Industrial CI already combines some of GATE's parts: Test Impact Analysis in Azure Pipelines selects impacted tests and falls back to all tests for changes it cannot analyse, such as unknown file types [34]; build systems at scale run the tests of affected targets [27]. Patch-coverage checks such as diff-cover fail a build when too few changed lines are covered by the suite [35]. They measure coverage by the whole suite, not by the tests that ran for the change, and they do not consider removed tests or the role of models. Agents can also pass a check by changing the tests: on tasks whose tests contradict the specification, frontier models modify or special-case tests instead of failing [33].

**Testing LLM and agent systems.** Two recent papers propose test pyramids for these systems: Badagi et al. [7] define five layers by the scope of what is tested and gate deployment with thresholds on LLM-judge scores, and Kohl et al. [8] apply the unit, integration, and acceptance pyramid to LLM-based agents in two case studies. Neither selects tests for a change or asks a person to approve one. GATE defines its layers by the kind of failure they find and includes a property-based layer, since mixing property-based with example-based tests finds more bugs [11, 12]. Work on making agents write tests [13 to 17] is a different problem, since GATE uses the tests a project has, and generated tests are often shallow or flaky [9, 10]; work on judging agent trajectories [18, 19] relates to the trajectory layer.

**How GATE differs.** The works above supply parts of GATE, and none supplies the whole. Safe selection [23 to 29, 34] decides which tests run and trusts its own list; patch coverage [35] checks the whole suite's coverage, not the selected run's. The LLM-based works use a model to inform an agent [30] or to rank tests [31], not to extend a safe core, and LLM reviewers [1, 2] let a model decide. The pyramid papers [7, 8] provide layers, not selection or approval. GATE's contribution is the combination and its tested safety: a deterministic core fixes the tests that must run, models may add tests and cannot remove any (Proposition 1), a changed file that no *selected* test reaches goes to a person, and so does a change that removes or weakens tests, which no selection tool or coverage check considers. A fixed rule turns the outcomes into a status that only a person with repository permission can override.
