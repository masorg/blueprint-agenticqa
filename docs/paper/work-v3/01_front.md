## Abstract

AI coding agents open pull requests faster than people can review them, so merging has become the bottleneck. The obvious answers fail: a language model that approves changes can be talked into approving unsafe ones, and running every test for every change does not scale. Test selection cuts the cost but opens a gap, because a gate that trusts its list of selected tests approves whatever the list omits. We present GATE (Guarded Approval from Test Evidence), a merge gate built on one rule: never approve on silence, that is, never when no executed test speaks to part of the change. A deterministic core selects the tests a change can affect, statically or from a stored coverage recording, and runs every test when unsure. Models may add tests, label them, and explain results, but they cannot remove a test or alter the verdict. A change that no selected test reaches, or that removes tests, goes to a person. We evaluate GATE against a full test run on {{selMutKilled}} + {{selHoldKilled}} failing mutants of {{shProjects}} Python projects (half of them pre-registered held-out projects), {{selSweUsable}} real SWE-bench defects, and {{shRan}} replayed real pull requests. GATE missed no failure, including all {{abPlainTotal}} cases in which its selection had omitted the failing test. On the same mutants pytest-testmon missed {{selTmMissK}} of {{selTmKilled}} failures, and in a misleading-text attack a model that decided pass or fail approved {{injBaselinePct}}% of failing runs, where GATE approved none. On {{dvSameN}} real pull requests GATE ran {{dvSameStaticPct}}% (static) to {{dvSameStoredPct}}% (stored coverage recording) fewer tests, and across {{shRan}} it sent only {{dvRevGreenPct}}% of the pull requests that a full run passed to a person. Hostile routers, classifiers, advisors, and pull-request text changed no verdict. Building and attacking GATE exposed nine fail-open defects in our own code, from which we draw four lessons for pipelines that put a model beside a decision.

**Index Terms:** pull-request review, regression test selection, LLM agents, merge gates, AI engineering

## 1. Introduction

AI coding agents have changed how many pull requests are opened. The AIDev dataset holds over 456,000 pull requests from five agents [20]. GitHub reports 43.2 million merged pull requests per month in 2025, 23% more than in 2024 [21], and vendor telemetry from over 10,000 developers shows that teams with high AI adoption merged 98% more pull requests while review time grew by 91% [22]. Producing a change is no longer the bottleneck. Merging it is [5, 22].

A merge needs evidence that the change does not break the project, and each of the common sources of that evidence has a weakness. A language model can review and approve, but review agents decide sooner without reviewing better [1], and the text of a pull request can talk them into approving unsafe code [2]. A person can review, but reviewers approve AI-written code more often as they see more of it [3]. Test results do not depend on how persuasive a pull-request description is or how tired a reviewer is, but running every test for every change spends the most compute where changes are most numerous. Regression test selection lowers that cost by running only the tests that a change can affect [23, 24, 25, 28].

Selection moves the risk instead of removing it. A gate that consumes the list of selected tests treats an empty or incomplete list as good news: the test that would have failed is never run, and the check is green. Safe selection tools fall back to a full run for changes they cannot analyse [24, 34], but within what they can analyse they trust their own list, and a patch-coverage check [35] measures the coverage of the whole suite, not of the tests that ran. Agents add a second route to a green check, because they can delete or skip the test that would fail [33].

This paper takes the position that a merge gate must *never approve on silence*. Silence is any lack of evidence: a changed file that no selected test reaches (imports, or executes under a recording), or a change that removes the tests that would speak. GATE (Guarded Approval from Test Evidence) applies the rule in three steps. A deterministic core selects the tests that a change can affect, from static dependencies or from a per-test coverage recording, made once and reused (*stored*) or made again for each change (*fresh*), and runs every test when it cannot account for the change. Language models may add tests, label them with a layer of a test pyramid, and write the report for the reviewer, but they can never remove a test or weaken the verdict. A fixed rule then computes the verdict: any failing test, any changed file that no selected test reaches, and any removed or weakened test sends the change to a person with write access, and everything else is approved. People remain the last step, but they see only the changes that the evidence cannot clear, together with the reason.

GATE is an AI-engineering artefact in two senses. It is a quality gate for software built with coding agents, including software with agentic components, for which its pyramid adds layers for tool-call trajectories and LLM-judged answers. And it is itself an AI-enabled system whose models may assist but are never trusted. Its design answers the question every team faces when it puts a language model into a delivery pipeline: what may the model decide? In GATE the answer is nothing; the model proposes, labels, and explains, and a deterministic rule decides. Models improve grouping and explanation; they are not needed for safety, which is the point.

Vendors whose software enterprise customers run in production, and those customers, including regulated enterprises, share five requirements that follow from this problem and from our own practice of building and operating the gate: throughput (R1), accountability for each decision (R2), safety against the change itself (R3), independence from any particular model (R4), and gradual adoption (R5). Table II defines them and maps each to a mechanism and to evidence (Section 3.7); they are our analysis, not a survey. GATE decides the test step of a merge, not the whole review: an organisation that requires human code review keeps it, and GATE tells the reviewer whether the tests show the change safe.

We evaluate GATE against a full test run, which is what a plain CI check does, on mutants of {{shProjects}} Python projects, on real defects, and on a replay of real pull requests in sandboxes. GATE missed none of the failures that the full run showed, and it did not depend on its selection to achieve this: in {{abPlainTotal}} cases the static selection contained no failing test, and the rule for unreached changes escalated every one of them. On the same mutants pytest-testmon, a widely used selection tool, missed {{selTmMissK}} of {{selTmKilled}} failures. A model that decides pass or fail from the same inputs as the gate approved {{injBaselinePct}}% of failing runs under misleading text, and GATE approved none. The contributions are the following.

1. **A merge gate that models cannot talk into approving (Section 3).** GATE separates what models may do (add tests, label them, explain the outcome) from what decides (a fixed rule over the selected tests, the unreached part of the change, and the tests it removes). A proposition states that no router, classifier, or test advisor can weaken the verdict, under two stated assumptions. A pyramid of five failure-class layers, two of them for agentic components, structures the reports and can be extended.
2. **No missed failure, including every case where the selection failed (Sections 5.1 and 5.2).** GATE missed none of the {{selMutKilled}} development and {{selHoldKilled}} held-out failing mutants or of the {{shRegress}} regressions in {{shRan}} real pull requests, and its static check selected or escalated all {{selSweUsable}} real defects. In {{abPlainTotal}} of these cases the static selection omitted the failing test, GATE caught {{abPlainTotal}} of {{abPlainTotal}}, and a plain selection gate would have approved all of them. Of the regressions, {{dvHard}} depended on the selection. pytest-testmon missed {{selTmMissK}} of {{selTmKilled}} failures on the same mutants.
3. **Large savings at a small review cost (Section 5.2).** On {{dvSameN}} pull requests the static core saved {{dvSameStaticPct}}% of the tests, and a coverage recording reused for up to {{stMapAgeMax}} commits saved {{dvSameStoredPct}}%, as much as a fresh recording for every change ({{dvSameFreshPct}}%). Across {{shRan}} pull requests GATE sent {{dvRevGreenPct}}% of those that a full run passed to a person, and a labelled sample shows which escalations were warranted.
4. **Three kinds of ground truth and a reusable evaluation kit (Section 4).** The evaluation combines mutants of {{shProjects}} projects, half of them pre-registered held-out projects, real defects, and {{shAttempted}} pre-registered real pull requests replayed in sandboxes. The replay harness, the pull-request manifests, the hostile-component tests, and the labelled escalations are released with the paper, and the replay runs in shadow mode on an organisation's own history (R5).
5. **Lessons from attacking and deploying the gate (Sections 5.3 and 6).** Hostile routers, classifiers, advisors, and misleading pull-request text changed no verdict after the two defects they exposed were fixed. The experiments exposed nine fail-open defects in our own gate, and deploying an earlier version on a managed platform exposed failures that hide a gate's output. We report the practices that found them.
